## 用户已明确的要求

1. 用户是明道云应用搭建工程师，服务不同业务类型；主要使用者是本人。
2. 核心问题是缺少系统方法，导致每个项目从头开始，经验没有沉淀。
3. 最需要补强需求分析、数据与流程设计、减少搭建错误和返工。
4. 初始需求可能非常少，业务接触人可能未知；需求逐步完善。
5. 所有阶段的产物都可以随需求修改；不能将前期产物视为永久定稿。
6. 每个阶段都要提供思路、设计指导、合理的问题和客观判断；不能无依据顺从，也不能为了反驳而反驳。
7. 需要有明确的项目开发阶段和细分步骤，参考成熟软件开发及零低代码实施方法，说明适配理由。
8. 希望最终具备分析、发现问题、搭建应用、生成交付材料的能力；不同阶段职责不同。
9. 工作流触发、审批等使用平台节点，复杂判断和数据处理优先考虑代码块。
10. 代码块要符合目标明道云环境的输入输出和依赖要求，参数、输出、注释尽量中文，便于排错。
11. 不包含培训、旧数据迁移、上线陪跑；包含需求、字段和流程的后续迭代。
12. 交付文档主要面向客户和领导演示，目前优先级靠后。
13. 实际项目产生的资料写入本地，并支持按用户指令拉取、更新 GitHub 内容。
14. GitHub 采用一个仓库、不同项目独立目录的组织方式。目录是资料组织边界，不是访问权限边界。
15. 用户自己搭建；未说明存在其他共同编辑者，但不能据此假定平台配置永远与文件一致。
16. 当前完成 skill 核心设计，后续用户会继续提出优化；验证阶段等用户明确提出。
17. 2026-10-24 用户已明确要求生成 skill 并上传 GitHub；本轮不自动安装、不运行实际业务案例。

## 当前设计提案，尚未经实际使用验证

- 采用 8 个工作阶段：建立项目；目标与范围；业务与规则；需求与验收条件；明道云方案；搭建；检查修正；发布交付。
- 阶段是工作视角。按当前需求选择相关步骤，可交叉、反复进入，不强迫整项目顺序通关。
- 使用稳定编号关联需求、规则、设计对象、代码和检查项；保留来源与修订记录。
- 分开记录需求确定程度、设计更新程度、实际实施状态和检查状态。
- 每轮先利用已有信息形成有依据的分析，再问真正影响下一步的问题。
- 在项目目录保存实施资产，在去除客户信息后单独整理可复用经验；不自动修改已安装 skill。
- 中文输入输出是用户偏好；2026-10-22 查得官方文档提示实际输出键应使用英文以避免使用方不兼容。当前设计采用英文输出键配中文说明、注释与结果信息，输入中文键在目标环境支持时使用。这是有依据的适配提案，未对用户样例或环境实测。
