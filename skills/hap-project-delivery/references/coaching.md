# 引导、任务选择与执行边界

## 1. 怎样选择当前工作

每轮先识别用户当前意图，再读取相关项目资料。一个项目可以同时有正在分析的需求和已经实施的功能，不能仅凭“项目处于搭建阶段”跳过新需求分析。

| 当前请求 | 优先处理 | 不自动附带的动作 |
|---|---|---|
| 从一句模糊想法开始 | 阶段 0、1，适量进入 2 | 不凭产品名字补成整套已确认需求 |
| 补充规则或纠正理解 | 更新阶段 2、3，分析对 4～7 的影响 | 不把追加一条文字当作全部变更完成 |
| 讨论某个实现方案 | 根据依据比较价值、限制和维护成本，更新设计草案 | 不把讨论方案视为平台执行授权 |
| 用户说“不懂”“不知道” | 解释相关概念与差别，提出条件明确的建议 | 不要求用户先自己写完整业务方案 |
| 要求搭建已确定内容 | 在明确环境、范围及已有授权内进入阶段 5 | 不重复询问每个已授权常规动作；不顺带上线其他功能 |
| 报错或效果不对 | 查现状与证据，定位到需求、设计、实现或环境问题 | 不以重新创建应用代替排查 |
| 用户手动改了应用 | 按 project-records.md比较旧依据、现状与拟改方案 | 不无条件恢复旧配置 |
| 要求拉取或上传资料 | 执行项目文件同步并更新状态 | 不自动应用到 HAP，不更新已安装 skill |
| 用户说“继续” | 依据项目状态续做当前任务，重新识别新消息中的限制 | 不跨越用户保留的生成、实际搭建或验证边界 |
| 用户要求停止某部分 | 保存已完成与待处理状态，继续其仍要求的独立工作 | 不把局部停止扩大成取消整个项目 |

用户明确要求讲解时先回答问题；不强行将每个解释请求转成下一阶段推进。

## 2. 提问与默认建议

判断是否要问的标准是：答案不同，是否会明显改变业务含义、数据结构、访问范围、实施成本或当前操作。

- 会产生明显差别且没有可用依据：说明差别后提出问题，阻塞依赖它的决定，独立分析继续。
- 不影响当前工作：登记待确认事项，在相关阶段再问。
- 有低成本、可逆且符合已知目标的默认做法：提出建议及理由，可以推进草案；不能冒充用户已经确认。
- 用户已经明确决定：记录并使用。只有新证据或矛盾出现才重新讨论。
- 用户明确否定或撤销旧要求：标记旧要求被替代，不把新旧版本并列为当前有效规则。

不要每轮重复整套问题清单；不要把多个没有关联的问题合成一长段；不要通过假设消除关键未知。

### 客观引导的表达

合理质疑应包含依据、影响和建议。例如：“目前规则要求提交后不可修改，但另一个场景又要求直接更改已提交记录。需要明确更正机制，否则权限和历史记录的设计会冲突。可以选择撤回后修改，或新增一条更正记录；两者对追溯的影响不同。”

这是表达方式示例，不是本项目的真实业务规则，也不是要求未来所有业务都采用这两种机制。

回复应随任务变化：分析时突出判断与关键问题；实施时突出实际结果与差异；解释时直接回答。不要每次都机械输出相同标题和表格。

## 3. 什么时候可以进入实际操作

执行意图以当前用户指令和已授予范围为准；默认协助工程师自行搭建，需要自动操作时按实际授权执行。

| 情形 | 运行约定 |
|---|---|
| 读取项目资料、查官方文档、维护设计草案 | 在相应任务范围内直接进行，重要假设标明 |
| 用户只确认方案“可以”“看起来没问题” | 不仅凭这句话推断其要求立即写入平台，结合上下文确定意图 |
| 用户明确要求实施某范围 | 已明确的环境与范围内持续执行，不逐对象反复确认 |
| 操作会造成已授权范围外的删除、历史数据转换或外部通知 | 先明确影响、具体对象和可行方案，再解决缺失的授权；不把一般搭建授权无限扩大 |
| 当前工具不能完成 | 给出准确人工动作及验证依据，保持待执行状态；能够独立完成的工作继续 |
| 用户要求前期完成后再生成 | “完成”指所选范围的前期准备足够，不要求所有未来需求永久冻结；生成的具体对象有歧义时在跨入该动作前澄清 |

平台节点和代码块的“测试”也可能产生副作用。未来执行前检查实际代码是否写数据、发通知或调用外部服务；优先使用不影响真实业务的检查条件。
