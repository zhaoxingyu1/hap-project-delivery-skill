# 需求分析与方案设计

## 1. 阶段运行方式

阶段 0～7 分别处理项目资料、目标、业务、需求、方案、实施、检查和交付。它们可以交叉和反复进入。

“当前足够继续”只针对某项需求或本轮范围，不表示整项目需求已经收齐，更不表示旧文件不可修改。设计过程中发现的新业务问题，应回到相应步骤处理并关联记录。

每步按以下结构执行：读取相关材料 → 说明本步目的 → 分析已有信息 → 给出理由与可选方案 → 提出必要问题 → 更新产物 → 标记下一动作及重访条件。

下文问题是示例，不是每次必问的问卷。用户已经给出答案或文件中已明确的内容不重复询问。根据缺口的重要性，通常每轮聚焦 1～3 个问题；不得为了数量限制拆散紧密相关的问题。

如果用户回答“不知道”：解释概念，用日常业务场景说明差别，给出建议及适用条件；允许标记未知。不要把业务设计工作交还给用户完成，不把默认建议自动升级成客户制度。

### 客观判断的具体要求

- 每项重要判断标明依据：用户确认、原始材料、平台文档、观察结果、推断或建议。
- 发现问题时说明“已有事实 → 冲突或不足 → 可能后果 → 可行处理”，证据不足时只标记风险或待核实。
- 区分业务必要性、平台可实现性、当前工具可操作性、维护成本和用户偏好。
- 用户明确选择一个可行方案后记录理由并推进；有新证据或实质风险变化再重新提出，不反复争论同一取舍。
- 不虚构客户岗位、业务制度、时间期限、并发量或验收人。找不到决策者时记录决策来源和局限。
- 把“实现成功”“检查通过”“用户验收”“客户正式认可”作为不同事实；只有相应证据才能标记。

## 2. 阶段 0：建立项目与恢复上下文

目的：让项目可续接，并保证本轮处理正确的项目资料。
输入：用户当前请求、已有项目文件、原始材料。

| 步骤 | 分析和动作 | 产物及判断 |
|---|---|---|
| 0.1 识别项目 | 确定新建还是续做，核对项目名称、目录和已知应用标识 | 不以同名应用或上次使用环境猜测当前目标 |
| 0.2 整理材料 | 登记材料来源和日期，阅读已有状态、未决问题和相关文档 | 缺失资料列为缺口；原文和分析结论分开 |
| 0.3 选择本轮任务 | 识别用户是补充信息、修改方案、要求实施还是询问解释 | “继续”按当前已授权任务续接，不自动跨入平台写入 |
| 0.4 建立或恢复记录 | 建立独立项目目录，记录本轮目标、相关文件和下一步 | 已有文件先读再改，不用模板覆盖 |

示例引导：“现有资料能说明目标，但没有明确谁录入、谁确认。我先梳理角色，不急着把它转换成工作表。”
当前足够继续：项目身份、当前请求和资料位置明确。GitHub 尚未配置不阻碍本地分析。
重访：切换项目、换设备、新会话、用户要求拉取、目录或平台配置发生变化。

## 3. 阶段 1：明确业务目标与本轮范围

目的：将产品名称或功能愿望转成具体业务问题，同时保留未来范围。
先读：原始诉求、项目概况、已有决策和目标；参考 sources.md 中的方法 S2、S1，步骤组织为本设计的适配。

| 步骤 | 怎样分析 | 怎样引导或质疑 | 更新产物 |
|---|---|---|---|
| 1.1 保留原始诉求 | 分辨目标、症状、参考产品和指定实现方式 | “你现在在哪个环节最费时间或最容易出错？”若用户不了解现状，先说明可探索的场景，不虚构痛点 | 需求来源、问题描述 |
| 1.2 找出业务结果 | 将“做个系统”转成某类使用者要完成的任务与改善结果 | 功能和目标无关联时指出；无法量化时先给可观察的结果，不编造节省比例 | 业务目标及判断方式 |
| 1.3 识别相关角色 | 区分操作人、规则提供者、数据负责人、决策与验收角色 | “谁录入、谁纠错、谁决定规则？”角色未知先记录，不以工程师意见冒充业务方确认 | 角色及待联系事项 |
| 1.4 调查限制 | 逐步识别交付时间、现有系统、使用端、平台环境和组织约束 | 只问影响当前选择的限制；不在信息不足时给精确工期承诺 | 约束与依赖 |
| 1.5 拆解参考产品 | 用户提出“完全参照”时列出已观察功能、未知规则、期望体验 | 区分功能、业务规则、界面、终端能力和集成范围；公开资料不能证明隐藏实现 | 参考范围及证据 |
| 1.6 提出本轮范围 | 将整体目标划成可形成完整业务结果的部分，说明依赖与取舍 | 不擅自缩水为演示版本；提出分批方案，由用户决定业务优先级 | 本轮范围、后续候选、暂不处理项 |

本阶段记录的目标保持可修改。“暂不处理”不等于永远不做，后续候选也不等于已承诺交付。
当前足够继续：可以说明主要使用者、至少一个目标场景、本轮预期结果；其余未知已标记。
重访：新增业务目标、使用人群、外部系统、截止时间、参考范围或交付边界。

## 4. 阶段 2：梳理业务流程与规则

目的：解释真实业务怎样发生，再判断哪些环节适合自动化。
先读：目标、原始单据或描述、相关角色、已有规则；参考 sources.md 中的方法 S1、S2。下列异常问题为本设计的检查建议。

| 步骤 | 怎样分析 | 怎样引导或质疑 | 更新产物 |
|---|---|---|---|
| 2.1 统一术语 | 为容易混淆的业务概念写简短定义，区分现象、事实和计算结果 | 同一个词有两种含义时先拆开；不要急着决定字段名 | 业务术语表 |
| 2.2 走一遍典型业务 | 从触发事件到最终结果，逐步列角色、动作、输入、输出和交接 | “从一笔业务开始，到什么结果才算结束？中间交给谁？”没有旧流程则设计目标流程，并明确它是建议 | 现状流程或目标流程草案 |
| 2.3 列业务规则 | 将规则写成适用对象、条件、动作或计算方式、例外、优先级、生效时间 | “遇到两个条件同时成立，按哪个处理？”把“通常如此”与强制规则区分 | 业务规则表 |
| 2.4 列状态与转换 | 确定业务对象有哪些状态，谁能以什么条件改变状态，变化产生什么影响 | 防止只列“待处理/完成”却无法说明撤回、作废、重新提交 | 状态转换表 |
| 2.5 补关键异常 | 检查遗漏、重复、超期、撤回、人员变更、失败和补处理等相关情况 | 按实际风险选择，不机械要求所有行业回答同一套异常题 | 异常处理规则、未决问题 |
| 2.6 改善目标流程 | 找重复录入、无意义审批、职责不清和无法自动判断的步骤 | 不把不合理的人工流程直接自动化；提出简化方案并说明影响 | 目标流程及取舍 |
| 2.7 对照实例核对理解 | 用已有业务实例检查规则表述是否一致；材料不足时用明确标注的假设示例 | 示例帮助理解，不作为真实需求证据；不同人说法冲突须记录来源 | 已确认规则、待决冲突 |

复杂分支适合规则表，跨角色交接适合流程图；简单业务可只写步骤，避免为形式画图。
当前足够继续：当前场景的正常路径、关键数据来源、关键分支及结束状态可解释；重大冲突有明确处理方向。
重访：新例外、新角色、新规则、撤回或补处理需求，以及方案设计暴露的业务矛盾。

## 5. 阶段 3：形成需求与验收条件

目的：把业务叙述转成有来源、可讨论、可追踪的实施需求。
先读：业务目标、流程、规则、约束；参考 sources.md 中的方法 S1、S8。下列字段及编号为本设计约定。

| 步骤 | 怎样分析 | 怎样引导或质疑 | 更新产物 |
|---|---|---|---|
| 3.1 按场景拆需求 | 围绕角色要完成的任务组织需求；分开业务目标与指定实现 | 不把“增加一个按钮”直接当作完整需求，补出按钮解决的任务 | 带稳定编号的需求 |
| 3.2 补齐需求内容 | 明确角色、触发条件、前提、输入、正常处理、异常处理和预期结果 | 缺少信息时解释它影响什么；低影响细节给可调整建议 | 需求当前版本 |
| 3.3 分析质量要求 | 按实际用途识别准确性、权限、时效、数据量、并发、可追溯和可维护要求 | “及时”“大量”“安全”不能直接用于验收；要求数值时说明依据，未知就标待定 | 质量要求及测量方法 |
| 3.4 排优先级与依赖 | 同时考虑业务价值、实现风险、前置条件及本轮资源 | 不把用户第一次提到的功能自动排第一；解释延后或提前的原因 | 本轮需求与依赖 |
| 3.5 写验收条件 | 从业务预期建立具体前提、动作、结果，包含相关边界和权限拒绝行为 | 预期结果不能仅由现有代码推导，否则可能把错误实现当成标准 | 关联需求的验收条件 |
| 3.6 检查需求质量 | 查歧义、重复、矛盾、遗漏、无业务价值的细节及缺失的来源 | 区分“描述清楚”与“值得实现”；提出替代方案，保留用户决定 | 问题清单与决定 |
| 3.7 标记确定程度 | 分开建议、待确认、已确认、推迟、被替代等状态 | 沉默不等于确认；已确认指当前版本而非永久不变 | 需求状态、确认来源 |

最小需求记录：编号、业务目标、来源、内容、验收条件、确定程度、修订号。复杂需求才展开更多字段。
当前足够继续：当前准备设计的需求有明确预期结果，关键未知不被掩盖；不要求未来所有需求同时确定。
重访：业务规则、验收口径、优先级或约束变化；实现暴露新需求或原需求不可行。

## 6. 阶段 4：设计明道云方案

目的：使数据、流程、权限、操作界面和代码共同满足当前需求，并能解释取舍。
先读：当前需求、业务规则、目标流程、已有对象记录；参考 sources.md 中的方法 S3、S4、S5、S7。以下细分设计为适配提案，不代表平台已具备所有列举能力。

| 步骤 | 怎样分析 | 怎样引导或质疑 | 更新产物 |
|---|---|---|---|
| 4.1 识别业务对象 | 说明每类对象是什么、一条记录代表什么、怎样唯一识别 | 不把每个功能都建成一张表，也不把不同对象仅因字段相似就合并 | 对象清单及记录粒度 |
| 4.2 设计对象关系 | 明确一对一、一对多、多对多，关系是否带数量、角色或有效期等信息 | 检查订单与明细等关系是否遗漏；多对多是否需要承载关系属性的独立对象按业务决定 | 关系图或关系表 |
| 4.3 设计字段 | 定义类型、含义、必填条件、来源、默认值、选项、校验、唯一性和编辑权限 | 名称相同不代表含义相同；默认值不能掩盖缺失；不能让“未知”默认为零 | 数据字典 |
| 4.4 处理历史与计算 | 区分原始事实、主数据、过程状态和计算结果；决定取最新值还是保留当时值 | “规则明天变化，昨天的结果要不要跟着变？”不能让关联变化无意改写历史含义 | 历史保留、生效期及重算策略 |
| 4.5 设计权限 | 按角色×对象×记录范围×操作×必要字段明确访问与修改边界 | 看不到某个视图不等于所有数据访问途径都受限；具体能力由目标平台文档核实 | 权限矩阵及能力待核实项 |
| 4.6 设计操作路径 | 按用户任务安排表单、视图、按钮、页面、移动端操作和必要统计 | 不以“页面齐全”代替任务可完成；不添加没有实际用途的仪表盘 | 页面/视图清单、关键操作路径 |
| 4.7 设计工作流 | 列触发事件、条件、读取与写入对象、状态变化、审批、失败处理和重复触发行为 | 检查循环触发、重复执行、部分写入及规则冲突；按实际影响选择处理 | 工作流说明及依赖 |
| 4.8 分配代码块职责 | 平台节点负责触发与审批等；复杂判断、计算和数据整理优先评估代码块 | 比较清晰度、平台能力、执行限制、接口成本和维护难度，不把所有步骤塞入一个代码块 | 节点分工、输入输出约定 |
| 4.9 核对可行性并划分实施批次 | 对关键未知查官方资料，记录版本和适用环境；必要验证须在获准时安排 | 缺少证据就标待核实，不能把工具暂不支持说成平台做不到 | 技术取舍、能力证据、实施依赖与批次 |

### 代码块设计约定

- 先定义职责和数据输入输出，再写实现。中文注释、参数说明、结果信息和排错说明优先；中文输入键在目标环境支持时采用。官方代码块文档提示实际输出键使用英文以避免使用方不兼容，因此设计默认采用英文输出键配中文说明，不宣称中文键在所有环境绝对不能运行。该取舍及证据详见 code-blocks.md。
- 输入约定包含来源、类型、必填、空值含义、格式和示例；输出约定包含稳定字段、类型及不同结果状态。
- 区分成功无数据、业务拒绝、执行失败和部分完成。返回“失败”字段不自动证明工作流会停止，后续节点须明确处理方式。
- 查询和写入行为要说明范围；只有发生外部写入时才讨论重复执行与部分成功的恢复方案，避免给纯计算添加无用复杂度。
- 列出目标语言和依赖。code-blocks.md 已记录官方文档中的运行环境线索，与目标环境实测状态分开；不将文档版本硬编码成永久通用规则，不补填尚无证据的运行时长或 API 配额。
- 提供输入输出配置说明、业务规则依据、失败排查方法；不要把鉴权值写入可提交代码、日志或演示材料。
- 代码参考只借鉴结构和风格；已有表和字段 ID 在实际项目核对后记录在该项目，不能当作通用常量。

当前足够继续：本轮方案能追踪到需求，关键模型和接口职责明确，重要能力疑点已列出；只有获准的实施范围才进入平台写入。
重访：字段含义、关联关系、角色权限、历史处理、规则、运行限制或工具能力发生变化。
