# 项目记录、变更与同步

## 1. 项目资料组织

采用一个仓库下多个项目目录，目录名在首次建立时确定并保持稳定。项目显示名称可以修改，避免每次更名都移动文件和丢失引用。

```text
projects/
  项目唯一目录/
    项目状态.md
    项目概况.md
    决策与问题.md
    需求清单.md
    业务流程与规则.md
    设计/
      数据模型.md
      权限与操作界面.md
      工作流设计.md
    实施/
      对象映射.json
      实施记录.md
      代码块/
    检查与交付/
    变更记录.md
    复盘.md
    材料/
knowledge/
  经验索引.md
```

- 首次只建立项目状态、项目概况和决策与问题；其他文件在确有内容时建立。
- 简单项目可以将业务、需求、设计放进一个文件的不同段落；规模变大再拆，并更新引用。
- 业务描述采用中文 Markdown；实际 ID 映射等需要工具读取的内容再使用结构化文件。避免同时维护相同事实的 Markdown 和 JSON 双份主记录。
- 原始材料保留来源和日期；客户隐私、密钥和完整原始日志不因“需要记忆”而全部纳入仓库。
- 客户演示材料来源于当前记录，但不是需求、设计和配置的主记录。
- skill 自身保存方法，项目目录保存项目事实。两者不同步混放。

## 2. 什么信息以哪里为准

| 信息 | 主记录 | 不一致时如何处理 |
|---|---|---|
| 业务预期 | 当前有效的需求和业务规则，附确认来源 | 新口头补充可能改变旧版本，先标识变更，不静默选择其中一个 |
| 设计理由 | 当前设计及决策记录 | 记录被替代方案与替代原因，当前设计只呈现有效方案 |
| 实际平台配置 | 指定环境下最近一次相关回读或可核实记录 | 平台现状代表已经配置了什么，不自动证明符合业务需求 |
| 检查结果 | 对应需求修订及实际实施版本的结果 | 依赖变化后标记待重查，旧结果只证明旧版本 |
| 仓库同步状态 | Git 本地与远端的实际状态 | 推送失败记录待同步，不宣称云端已保存 |

“最新修改时间”不是内容正确性的判断依据。实际平台、业务预期和方案之间的差异，应作为待处理事项保留。

## 3. 编号、状态与追踪

按需要使用：REQ-需求、RULE-规则、OBJ-设计对象、WF-工作流、CHK-检查项、DEC-决策、CHG-变更。编号跨改名保持稳定，不为了填满模板给每个小段落编号。

需求与规则记录来源、当前修订、关联目标及相关设计。实施对象记录项目内逻辑编号、环境、应用 ID、对象 ID 和最近核对时间；不同环境的 ID 不能混用。

需要分别记录的状态：

- 需求确定程度：建议、待确认、已确认、推迟、被替代。
- 设计状态：草案、当前可用、受变更影响待更新。
- 实施状态：未实施、部分实施、已实施、现状待核对、执行失败。
- 检查状态：未检查、通过、不通过、因变更待重查。

一项需求可以同时是“已确认、设计已更新、平台待修改、检查待重做”。不能只显示一个笼统的“完成”。

初期通过文档内的关联编号维护依赖；复杂到人工追踪易遗漏时再考虑生成结构化依赖索引，不预先构建大型管理系统。

## 4. 每轮对话的更新过程

1. 读取项目状态、当前请求涉及的资料和未决问题；不要无差别加载整个仓库。
2. 分辨用户是在补充事实、探索选项、提出建议、作决定还是要求实施。
3. 判断新增信息是否影响已有目标、规则、数据、权限、工作流、代码或验收条件。
4. 给出判断依据；关键歧义先问，独立于该歧义的分析继续进行。
5. 用户已明确的事实或决定写入有效正文；助手建议和未确认部分明显标注。
6. 同步更新本轮能够确定的关联文件；不能更新的标明待处理原因，不能编造补齐。
7. 保存项目状态：本轮变化、相关文件、未决问题、下一步、平台是否有实际变更。
8. 报告保存结果及重要差异。写入失败要说明，没有写成功不能说“已经记住”。

有实质结论或变更时及时保存，不等阶段结束。没有新增信息的寒暄或解释不产生无意义版本。当前会话新增资料若尚未得到具体业务结论，可以登记原文和待分析状态。

跨多个文件更新时，先在项目状态中登记受影响条目，再更新正文，最后更新状态及链接。如果中途停止，未更新文件保留“受影响待更新”状态；不能因为其中一个文件写完就标记全部同步完成。保存前若发现用户修改了同一内容，重新读取并保留其意图，语义冲突进入待决事项。

## 5. 一次变更如何处理

### 5.1 先判断变更性质

- 尚未实施的草案补充：直接更新当前草案，保留重要来源与决定；无需每次建立正式变更单。
- 影响已确认设计、实际应用或检查结论：建立变更记录并说明影响。
- 仅修正文档措辞且语义不变：轻量记录，不触发整项目重新设计。

### 5.2 分析影响

从变更条目沿关联编号检查：

```text
业务目标或规则
  → 相关需求及验收条件
  → 表、字段、关联、历史数据含义
  → 权限、操作路径、工作流、代码、接口、统计
  → 已实施对象
  → 受影响检查项和演示材料
```

不机械修改所有文件，只更新实际相关部分；无法确认影响范围时明确说明分析不完整。

### 5.3 记录决定并更新

最小变更记录包含：原因、来源、旧含义、新含义、受影响条目、建议方案、用户决定、文档状态、实施状态、检查状态。

确定删除字段、改类型或改变历史含义前，检查现有数据和下游依赖，说明可行替代方式及恢复限制。范围和权限已明确时按授权执行，不把每个常规可逆操作都变成审批。

用户不包含旧数据迁移的交付范围，不能被解释为允许忽略迭代对已有数据的影响。若变更必须转换历史数据，应说明依赖并就新增范围取得决定。

## 6. 中断、恢复和人工修改

项目状态至少记录：项目标识、当前焦点、本轮范围、最近结论、待决定问题、受变更影响的产物、下一动作、文件链接、已知环境及同步状态。

恢复顺序：

1. 确定项目目录，读项目状态。
2. 读取当前请求对应的需求、设计和未决问题。
3. 对照用户新指令，标记旧计划是否仍适用。
4. 若本轮涉及实际应用，读取相关现状；文档讨论无需每轮连接平台。
5. 对未完成的操作先确认现状，再续做，避免重复创建。

用户自己也可能直接改明道云配置。发现差异时列出设计预期、平台现状和可能影响；不能自动以旧设计覆盖人工修改，也不能把平台上的每项改动自动认定为已确认需求。

具体比较三份信息：最近一次有证据的配置、当前平台配置、本轮拟改方案。人工修改与本轮无冲突则保留并更新记录；有业务含义冲突才提出问题。没有最近配置证据时说明无法完整判断改动来源，不凭时间猜测是谁改了什么。

缺失关键材料时说明缺失，不通过概括性的记忆填补具体字段 ID、规则或执行结果。只阻塞依赖该材料的动作。

## 7. GitHub 同步设计

规则属于 skill，上传内容属于项目实施资产。

- 首次建立业务项目时创建本地独立目录；已指定并授权的仓库可按用户同步要求提交该目录，使远端出现对应项目目录。
- 没有仓库地址或访问方式时，继续本地设计，登记“云端未配置”；首次实际同步时再解决，不提前索取凭据。
- “拉取更新”默认指项目资料同步，不意味着更新 skill，更不意味着把拉取的方案直接应用到 HAP。
- 拉取前检查本地修改、分支和远端差异。无冲突正常更新；有语义冲突时比较双方内容，不能用远端版本强制覆盖未保存工作。
- 推送前检查变更范围，明确选取目标项目文件，避免将同仓库其他项目的未完成改动一起提交。
- 密钥、令牌、密码、未脱敏客户数据及不必要原始日志不进入版本历史；私有仓库也不是运行时密钥存储方案。
- 文档内部普通修订通过 Git 记录；关键业务取舍另有决策记录。未经用户同步指令或持续授权，不自动推送。
- 推拉后核对结果，更新同步状态。Git 回退只恢复文件版本，不能被描述为已回退明道云配置。
- 一个仓库内的目录没有独立访问权限；不同客户需要独立授权时再评估分仓库，不在当前设计中擅自改变用户选择。

## 8. 经验沉淀与复用

项目复盘记录问题情境、根因、处理方式、设计理由、适用条件和实际结果。优先记录影响设计或反复出现的问题，不把每个小操作变成知识条目。

跨项目经验条目应包含：问题模式、适用与不适用条件、方案及取舍、证据状态、相关平台版本或日期、脱敏来源引用。

只有当前项目记录证明有效的处理方式才能标记“已在某类情境使用”；仅分析得到的方案标记“建议，未实践”。不要因为写入经验库就宣称普遍适用。

新项目在已知业务场景后检索相关经验，再判断背景和约束是否匹配。复用方法或模板时清除客户信息、业务 ID、鉴权值和特殊制度；不把原客户规则原样复制。

经验库默认随项目工作维护，已安装 skill 的通用规则不会自动被某个项目改写。用户要求优化 skill 时，再从已积累证据选择可泛化的改进。
