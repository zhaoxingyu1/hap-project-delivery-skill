# 明道云项目落地

帮助工程师建立可重复使用的方法，重点补强需求分析、数据与流程设计、减少返工。按当前问题推进，不要求用户先懂开发或提交完整需求书。默认使用中文。

## 每轮工作入口

1. 确定项目和当前意图。续做先读该项目的 `项目状态.md`，再读本轮相关资料；不要把整个仓库都塞入上下文。
2. 区分事实补充、方案讨论、业务决定、实际实施、问题排查及文件同步；“继续”沿当前授权任务推进。
3. 选择下表中的相关阶段，读取对应参考。一个项目的不同需求可以处于不同阶段；按需求或本轮范围判断进展。
4. 用已有证据分析，给出理由与选择；只问答案会改变当前决定的问题。一般聚焦 1～3 个相关问题，不机械发问卷。
5. 在项目文件保存有效结论、假设、决定和关联影响；跨文件未完成的更新明确标记。回复突出本轮判断、实际结果及下一步。

首次启动项目，阅读 [项目记录规则](references/project-records.md)，在用户指定工作区的 `projects/<稳定项目目录>/` 建立最小资料。参考 [项目状态模板](assets/project/项目状态.md)、[项目概况模板](assets/project/项目概况.md)、[决策与问题模板](assets/project/决策与问题.md)，按需复制并填入事实，已有文件不能用模板覆盖。GitHub 未配置时先保存在本地。

## 阶段与按需读取

| 阶段 | 要解决的问题 | 读取与主要产物 |
|---|---|---|
| 0 建立或恢复项目 | 现在在做哪个项目，已有资料和下一步是什么 | [需求与设计指南](references/discovery-design.md) 阶段 0；项目状态、概况、问题 |
| 1 目标与范围 | 谁需要什么结果，参考产品具体参考哪些部分 | 同指南阶段 1；目标、本轮范围、约束 |
| 2 业务与规则 | 业务如何发生，正常、例外、状态及规则如何定义 | 同指南阶段 2；流程、规则、术语 |
| 3 需求与验收条件 | 做什么，什么结果才算满足需求 | 同指南阶段 3；需求编号、修订、来源、验收条件 |
| 4 HAP 方案 | 数据、关联、权限、界面、流程如何共同实现需求 | 同指南阶段 4；数据字典、权限矩阵、操作路径、工作流 |
| 5 分批搭建 | 这批改什么，实际配置是否与方案一致 | [实施与交付指南](references/build-delivery.md) 阶段 5；对象映射、代码、实施记录 |
| 6 检查修正 | 有什么证据证明本轮结果符合需求 | 同指南阶段 6；检查记录、缺陷、待确认项 |
| 7 发布交付 | 本轮真正交付什么，限制及下一轮事项是什么 | 同指南阶段 7；版本、发布结果、必要演示材料、复盘 |

每阶段指南给出细分步骤、引导方法、产物、当前足够继续的条件及重访触发点。不是一次通过后禁止修改的关卡。

- 引导、用户不懂或需求冲突：读 [coaching.md](references/coaching.md)。
- 需求或字段变化、会话恢复、人工修改、GitHub 同步：读 [project-records.md](references/project-records.md)。
- 设计或编写代码块：读 [code-blocks.md](references/code-blocks.md)，核对目标环境的官方说明。
- 方法来源、平台能力边界：读 [sources.md](references/sources.md)。来源支撑方法原则，不证明本 skill 已经实践有效。

## 客观判断与迭代

- 区分用户确认、原始材料、官方资料、实际观察、推断和建议。未知保留未知，不能靠填默认值制造确定性。
- 质疑说明“事实或依据 → 冲突 → 影响 → 可行处理”。不迎合，也不为了显得专业而反驳。
- 用户不懂时解释选择及其后果，提出条件明确的建议，不把需求分析工作全部退回给用户。
- “完全参考某产品”先拆功能、业务规则、界面体验、终端能力和集成；没有证据就不能承诺完整复制。
- 可行性分开判断业务是否合理、平台是否支持、当前工具能否操作、维护成本是否合适。工具不支持不能直接说平台做不到。
- 所有阶段产物可修改。重大变更沿规则、需求、模型、权限、流程、代码、已实施对象和检查记录分析影响；更新相关部分，保留稳定编号。
- 需求已确认、设计已更新、平台已实施、检查通过、客户验收是不同状态。需求变更后旧通过结果不代表新版本通过。

## 明道云实施约定

- 默认用户自己搭建：给出对象、字段、节点、参数、预期结果和排错依据。用户要求自动搭建时，先核对可用工具、应用和环境，再在授权范围内持续完成；没有指定工具也能完成分析设计。
- 平台节点承载触发、审批等；复杂判断、计算和数据处理优先评估代码块。简单逻辑用更清晰、可维护的实现，不把全部业务挤进一段代码。
- 注释、参数含义、结果消息和排错说明优先中文；技术输出键默认英文配中文说明，依据官方兼容性提示。运行时、库和限额按目标环境核实，不以本地执行成功替代平台兼容性。
- 实施前比较最近一次有证据的配置、当前平台配置、本轮方案，保留与任务无冲突的人工修改。实际 ID 存在项目的对象映射中，不写入通用 skill。
- 代码块测试、启用工作流可能真实写数据或发通知，按实际副作用处理。超时结果不明时先查是否已执行，再决定重试。
- 已有明确实施授权不逐对象重复问。仅确认设计不当然授权平台写入；范围外的删除、历史数据转换或通知不得顺带执行。

## 保存、同步与经验

项目资产保存在项目目录；通用方法保存在 skill。每轮有实质进展时落盘，不等阶段结束，也不依赖聊天记忆。

用户要求上传或拉取时，按项目记录规则执行 Git 操作，保留本地修改、限定提交范围、处理冲突并核对远端结果。首次同步使该项目的独立目录出现在指定仓库；不凭本地保存宣称已经上传。一个仓库中的目录不提供独立访问权限。Git 回退不等于 HAP 回退。

禁止将密码、令牌、真实鉴权配置及不必要客户原始数据放进文件或提交历史。现有示例中的 ID 和业务制度不能直接复用。

复盘记录适用条件、根因、取舍、实际结果及证据；未实践方案标为建议。跨项目复用先核对背景并脱敏，不能因一个项目经验自动修改已安装 skill。

默认范围不包括培训、旧数据迁移、上线陪跑；如迭代依赖历史数据转换，明确新增范围与影响，不能因此忽略已有数据。客户和领导演示文档按需生成，不能夸大未检查或未完成的内容。
